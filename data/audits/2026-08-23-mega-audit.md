### Same-day PORDATA updates are permanently missed: staleness uses strict '>' on date-only lastmod

*assumptions · ADJUSTED*

- **Evidence:** scripts/harvest_catalogue.py:140-141 (`mods[u] > rec["harvested_at"]`) compares two date-only strings: lastmod is date-only ISO in every one of the 5,906 rows of data/sitemap-lastmod.tsv (measured: `cut -f2 data/sitemap-lastmod.tsv | grep -vE '^([0-9]{4}-[0-9]{2}-[0-9]{2})?$'` returns nothing), and harvested_at is written as %Y-%m-%d (harvest_catalogue.py:127). A page harvested on day D whose PORDATA lastmod then moves to D (e.g. harvested by the 09:07 UTC dispatch, edited by PORDATA that afternoon, seen by the 18:23 UTC watcher) yields 'D' > 'D' == False: never stale. The only test, tests/test_harvest.py:47-63, uses distinct dates (2026-08-15 vs 2026-08-01) and never exercises the equal-date boundary. The sitemap watcher's dispatch gate (sitemap.yml, 'pending pages' step) uses the same plan(), so no harvest is even dispatched for these pages.
- **Impact:** Silent wrong data: the record's fontes/ultima_atualizacao/name stay frozen at the pre-update fetch forever (until PORDATA touches the page again on a later date). Nothing in QA can see it because the stored record is internally consistent.
- **Fix:** Change the staleness comparison to `mods[u] >= rec["harvested_at"]` (worst case: a page whose lastmod equals today's harvest date is re-fetched once per run until the calendar day passes, bounded and cheap at 1 req/20s), or store a full timestamp in harvested_at and compare `lastmod >= harvested_at[:10]`.
- **Prevention:** Add a unit test to tests/test_harvest.py: a record with harvested_at == lastmod (same date) must appear in plan()['stale']. The current mutation-testing gate would then also kill any '>' vs '>=' mutant.
- **Verifier adjustment:** Mechanism reproduced; scope and severity overstated. Verified: harvest_catalogue.py:140-141 compares `mods[u] > rec["harvested_at"]`, harvested_at is written `%Y-%m-%d` (lines 127 and 201), and lastmod is date-only in every row — measured `cut -f2 data/sitemap-lastmod.tsv | awk '{print length($0)}' | sort | uniq -c` → 4423 rows of length 10, 1483 empty, nothing else (5906 total). sitemap.yml:91-94 does call the same `h.plan()` for its dispatch gate. The test gap is real: tests/test_harvest.py:47-63 uses 2026-08-15 vs 2026-08-01 and 2026-08-10 vs 2026-08-20, never the equal-date boundary. Corrections: (a) the title overreaches — same-day *publishes* are caught fine, because a page published on day D that was last harvested on an earlier day gives D > D-n (this is exactly what the 18:23 UTC run in sitemap.yml:17-23 is for). The only lost case is a page PORDATA touches a *second* time on the same UTC day, after our fetch that day; (b) current exposure measured at zero — I computed `sum(1 for u,r in load_records().items() if lastmods().get(u)==r['harvested_at'])` = 0 of 2196 records (harvested_at is 2026-08-22/23; the only 2026-08-23 lastmods are the 7 hub pages, which `targets()` excludes). It is a latent correctness bug, not a currently-firing one. Severity medium → low. Fix (`>=`) and the equal-date unit test are both right; note `>=` re-fetches a page once per run for the remainder of the UTC day it was touched, which is bounded and cheap at 1 req/20s.
